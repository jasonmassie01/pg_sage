**What runs autonomously today.** Once the ramp has elapsed under `trust.level: autonomous` with tier3 flags set, everything SAFE or MODERATE in `action_contract.go` can run unattended in-window. That covers analyze, vacuum, index create/drop/reindex, GUC changes, autovacuum per-table settings, query hints, create statistics and retention deletes. Backend signals and HIGH always need a human (`gate.go:118-121, 392-394`). The earned ledger restricts only actions that carry an `IncidentFamily`, and **only custodian proposals set one** (`executor/custodian.go:107`, `executor/autonomy.go:49-57`).

## 2. What is weak

1. **Promotion above L1 is impossible without CI, and the UI cannot do the human part.** L2 needs `bench_present`/`bench_fresh`, i.e. a PGIncidentBench report ≤30 days old that has gated cells for the family (`earned/evidence.go:209-219, 251-269`). Fast elevation deliberately leaves bench age and n untouched (`cmd/pg_sage_sidecar/fast_elevation.go:14-16`). `LatestBench` reads only `source='bench'` (`earned/store_evidence.go:194`), and game days "only restrict" (`evidence.go:343-345`), so a user with no CI artifact can never reach L2. The shadow review that feeds L2 is API-only. `POST /sre/autonomy/reviews` (`api/autonomy_handlers.go:57`) has no caller in `web/src`. The MCP tools only read and downgrade (`mcp/autonomy_tools.go:41-45`). There is no "evaluate now" button either: `POST /evaluate` exists (`:51`) but the page never calls it (`web/src/pages/AutonomyPage.jsx:75-81`). The user's "nothing was proposable" is the designed result. The page shows the unmet checks as raw names (`AutonomyPage.jsx:226-239`) and never says how to satisfy them.
2. **Two trust systems that never meet.** The actions that actually ran on lifeos (19 index drops, `maintenance_work_mem`) went through the elapsed-time ramp, not the earned ledger (`policy/autonomy.go:63-67`). The ramp is a single `RampStart` for all action types (`executor/policy_runtime.go:63`, `schema/bootstrap.go:116`). Nothing about outcomes affects it: no rollback, regression or `harmful` record lowers it. An action type added in a later release is autonomous on the day it ships if the ramp has already elapsed. That contradicts the config doc ("gate newly-supported actions behind a soak period", `config/config.go:208`).
3. **Most of the 11×N ledger grid is inert.** Only wraparound and WAL pairs ever get self-initiated requests. lock_blocking, plan_regression, checkpoint and the rest show levels and "next" checks in the UI, but no code path produces a family action for them. The SRE action service derives only `cancel_backend` (`sre/action/derive.go:45`), which always needs approval.
4. **The post-action verification for drops and GUCs barely measures anything.** If the finding has no queryids (unused-index drops, GUCs), the monitor compares the *cumulative* `blks_hit/(blks_hit+blks_read)` from `pg_stat_database` and the *cumulative* unweighted `avg(mean_exec_time)` of statements matching `LIKE 'INSERT%'/'UPDATE%'` (`executor/rollback_eval.go:26-33, 42-75`). Both are point reads against since-reset counters (`executor.go:781-814`), so a 15-minute window (`config/defaults.go:51-52`) almost cannot move them (inferred). The write-latency bar is a hard-coded 20% (`rollback_eval.go:72`). "Verified, none regressed" for the 19 drops is therefore weak evidence. A dropped index hurts rare queries such as month-end jobs, which no 15-minute window sees.
5. **"Verified recovery" can mean "not verified".** The reconciler counts `outcome='success'` with an empty verification as `verified_recovery` (`earned/reconcile.go:127`). This is the same counter L3 promotion uses (`evidence.go:227`).
6. **The verify engine has no noise model.** It compares means. It reverts if *any* target query got worse by more than RegressPct and keeps the change if *any* got better (`verify/evaluate.go:118-150`). There is no variance, no significance test, and no control for workload mix. With many target queries, at least one false regression becomes likely (inferred).
7. **Blast radius is mostly unmeasured.** `usage.RowsRewritten` and `usage.StorageBytes` are never assigned anywhere. `standingUsage` fills only change and table counts (`executor/policy_runtime.go:82-107`), so `max_rows_rewritten: 5000000` (`policy/document.go:343`) cannot trigger. Load admission runs only for index builds (`executor/load_admission.go:75-81`, `custodian.go:42` vs `:135`). Drops, VACUUM FREEZE and GUC changes get no CPU/IO check and no size, lock or WAL estimate.
8. **Contract pre- and post-checks are prose.** `Prechecks`, `SuccessCriteria` and `PostChecks` in `executor/action_contract.go` have no consumers (grep finds only two other literals). The contract promises "index does not already cover target columns" and "disk pressure below threshold", but the gate never evaluates them.
9. **Anti-oscillation misses in-flight actions.** `exceedsOscillationLimit` counts only terminal outcomes (`executor.go:689-692`). Drops still in their 15-minute `monitoring` state do not count. That is a plausible cause of "8 drops in 40 minutes" (inferred). The app-managed memory now fixes the symptom, but only after the index has come back at least once.
10. **Cap inconsistency for the WAL bound.** The class spec caps `wal_bound` at L2 as mitigation-only (`earned/class.go:94`). `carryCap` lowers only *irreversible* classes (`carryover.go:61`), and the WAL proposal travels as `alter_system_guc` with rollback class `reversible` (`action_contract.go:279`). The carried WAL bound can therefore reach L3 auto-execute, even though the spec says a slot past the bound is lost. `guc_guard.go:43-58` mitigates this.
11. **An irreversible action is autonomous above L1.** `retention_delete` is `not_reversible` but MODERATE (`executor/retention_apply.go:98-126`). With an owner declaration it passes `unrollbackable` (`policy/refusal.go:28-30`) and runs after the ramp, outside the ledger. This was a deliberate decision (D5), but it conflicts with the stated principle.
12. **Clone simulation is barely wired.** The `snapshot` provider errors in production (`mcp_migration_runtime.go:22-26`). Game days run the deterministic investigator only: no executor, no gate, no LLM arm (`sre-bench/gameday.go:80-84`). Nothing rehearses an index drop or GUC change on a clone before production.
13. **L3 bar vs. reality.** L3 requires 50 verified L2 recoveries per pair (`evidence.go:105-111`). Wraparound freezes happen a few times a year, so L3 is reachable only through carry-over (inferred).
14. **pg_sage's own footprint is outside policy.** Budgets have `storage_bytes` (`document.go:57-61`), but it is never measured (item 7), and `sage.*` retention is purely time-based (`retention/cleanup.go:131-134`). This is consistent with the 9.3 GB of snapshots on lifeos. The forecaster overload was pg_sage's own read workload, which no admission check covers (inferred, outside this package set).

## 4. Expand

- **One trust model.** Fold the ramp into the ledger. Every self-initiated action gets a pseudo-family (`maintenance`, `index_hygiene`, `config_tuning`) so index drops, GUCs and retention earn L2/L3 from their own outcomes with the same downgrade signals. The ramp becomes the L1→L2 time floor, not the authority.
- **Shadow mode for every action class.** At L1, record the action pg_sage *would* have taken (SQL, predicted effect, verify plan) as a `shadow_action` row. Later, score it counterfactually: did the problem self-resolve, did a human take the same action, would the predicted gain have held (HypoPG `EXPLAIN` for index changes, workload replay for GUCs)? Shadow precision then becomes promotion evidence that replaces manual packet reviews for non-incident classes.
- **Pre-flight on a clone** (DLE now, snapshot once wired). For a drop: restore a 24 h `pg_stat_statements` sample and replay the top queries before and after the drop. For a GUC: run a pgbench-style replay. For DDL: measure lock duration, WAL bytes and rewrite. The clone result becomes a contract precondition at L3.
- **Blast-radius model.** Before an action, predict lock mode × duration, WAL bytes, IO bytes, replica-lag impact and the set of affected queryids. Compare it with what was observed afterwards; prediction error per class becomes a promotion and demotion signal.
- **Drop quarantine.** Today a drop counts as "reversible", but reverting it means a full rebuild. Add a soak step first: hide the index from the planner for a full business cycle with `pg_hint_plan` hint rows (already an action class), watch the affected queries, then drop. The first step then really is reversible (inferred feasibility; needs `pg_hint_plan`).
- **New action classes:** per-role `idle_in_transaction_session_timeout` (reversible GUC), per-table `fillfactor`, partition maintenance (L1 first), and leaked `test_*` schema cleanup (irreversible → L1 script only).

## 5. AI-first redesign

**What the model decides.** The deterministic analyzers keep proposing candidates. The model takes over three jobs it handles better than rules:
1. **Plan.** Given a finding plus context (workload sample, table size, replicas, app-migration history, prior outcomes on this object), the model writes an *action plan*: SQL from a typed template, a predicted effect per affected queryid (latency delta, IO delta), a blast-radius estimate, a verification plan (which queries, how long, what counts as success), and a revert trigger.
2. **Judge.** After the action, the model reads the verification data and writes the verdict and its reason. Statistics decide revert or keep. The model explains, and flags confounders such as a deploy, a batch job or a failover.
3. **Promote.** The model writes the promotion case: evidence, counterfactuals, risks. The human approves or rejects it. This replaces the bare check list in `AutonomyPage.jsx`.

**Tools (MCP / tool calls, all read-only except one).** `explain_hypothetical(sql, index_def)` (HypoPG), `workload_sample(table, window)`, `object_history(obj)` (action_log, app-managed status, migration events), `clone_preflight(plan)` (DLE), `estimate_blast_radius(sql)`, `ledger_level(family, class)`, and `propose_action(plan)`. The only mutating tool is `propose_action`, which goes to `Executor.Apply`. The model never gets raw SQL execution.

**Validation.** The plan must parse into the typed contract (`ContractForActionType`). The SQL must match the template and pass AST validation (`executor/validate_ast.go`). Predicted effects must reference queryids that exist in the sample, and blast radius must stay within the policy document. Every claim cites an evidence ID (the SRE `sre_evidence` pattern). If validation fails, the plan parks; it never falls back to execution.

**Evaluation.**
- *Replay bench*: store 30 days of lifeos-style snapshots and judge each historical candidate with the model. Score the predicted effect against what actually happened for actions that ran, and the counterfactual (HypoPG/clone) for those that did not.
- *PGIncidentBench action arm*: extend fault programs so the executor and gate run on the clone, then score Safe Pass on *actions*, not diagnoses. Today game days skip the executor.
- *Shadow mode*: L1 classes log model plans continuously. Precision = accepted-or-later-equivalent / proposed.
- *Outcome ledger*: `sre_autonomy_outcomes` plus prediction error per class. Calibration (predicted vs. observed effect) is a promotion check, so a model that is often wrong cannot be promoted.

**Learning.** Per object and class, the model retrieves past outcomes (object_history) into context. Repeated reverts on an object set a durable "do not touch" memory, generalizing app-managed indexes. Retrieval plus calibration gates is enough; no fine-tuning.

**Cost control.** Planning calls happen only for candidates that pass the deterministic gate pre-check (`Gate.Explain`, `policy/gate.go:27`), so there are no model calls for actions that would be blocked anyway. Use a cheap model (gpt-6-luna class) for plan and judge, and a larger one only for promotion cases (weekly). The policy budget `llm_tokens_daily` (500k, `document.go:344`) already exists; meter it per class. Cache plans by `(finding identity, workload hash)`.

**Guardrails unchanged.** Gate and Apply stay the only authority, irreversible ≤ L1, a human approves every promotion, the e-stop stays, and downgrade signals still apply. The model only adds evidence and predictions.

## 6. Top 5

1. **Make promotion achievable and explain itself (I1 + I2).** The ledger works, but a non-CI user cannot use it: L2 needs a CI bench report and API-only reviews. Add Accept/Reject on concluded investigations, an "Evaluate now" button, and a local bench run on a clone or local DSN that counts as bench evidence for the families it covered. Then turn each unmet check into an instruction. This is the cheapest fix for the dogfood complaint.

2. **Unify the two trust systems.** The actions that matter most (index drops, GUC tuning, retention deletes) run on a time-only, outcome-blind ramp. The evidence-based ledger governs only the custodians. Give every self-initiated class a ledger pair, make the ramp a time floor, and let rollbacks and harmful outcomes demote (I5, I6).

3. **Replace the global-metric rollback check with real measurement (I3, I4).** The monitor reads cumulative counters for 15 minutes, and "success without verification" counts as a verified recovery. Use snapshot deltas weighted by calls, cover a business cycle for drops, add a variance-aware test, and stop crediting unverified outcomes.

4. **Measure blast radius and pre-flight on clones.** Fill `RowsRewritten`/`StorageBytes`, run load admission for every MODERATE action (I9), turn contract prechecks into code (I10), and add predicted-vs-observed impact per action. Next, wire the snapshot clone provider and add `clone_preflight` for drops and GUCs. Prediction error then becomes a promotion signal.

5. **Shadow mode with counterfactual scoring as the default way to earn autonomy.** At L1, record every action pg_sage would take with its predicted effect and score it with HypoPG, workload replay and later human behaviour. That gives volume (thousands of shadow decisions instead of 3–20 hand reviews), lets new classes start safely at L1, and gives the §5 planner a measurable precision to be promoted on.
