# dev.11–12: organization sharing, classic memes and App availability

This follow-up covers the development changes after the dev.10 documentation
publication. It does not replace the earlier Lakebase compatibility matrix or
claim a new whole-repository suite. The latest complete repository run remains
the [dev.5 acceptance](2026-10-30-v2.5-dev5-acceptance.md).

## Organization sharing

The development App grants the account's built-in `account users` group
`CAN_USE`, preserving its owner and inherited administrator management grants.
That group includes non-employees, so the application first received an exact
`databricks.com` email-domain gate. Protected requests check that policy before
any durable account lookup or provisioning, including existing administrators.
New recognized identities default to viewer. Neither App access nor an email
domain grants operator rights, database privileges or change approval.

Databricks sign-in remains the only sign-in. Platform account identity and the
organization's SSO/onboarding remain prerequisites: this change does not
provision all employees into the account, establish current employment from an
HR directory, or bypass IdP policy. Static dashboard assets and health/auth-mode
discovery can pass platform ingress; protected API data require the audience
check. A second employee identity and an actual disallowed-domain identity were
not available for a live sign-in test. Those gate paths have local tests.

Public reference: [Databricks Apps permissions](https://docs.databricks.com/aws/en/dev-tools/databricks-apps/permissions).

## Meme refresh

Six recognizable templates replace the original drawings: Drake, Distracted
Boyfriend, Two Buttons, Disaster Girl, Change My Mind and This Is Fine. Each
page has its own Postgres caption. Accessible HTML labels describe the image's
roles; compact images stay secondary to the operational content. Images are
bundled locally, lazy-loaded and served from the App origin. The browser has
no runtime dependency on the source image host.

[Credits and provenance](../sidecar/web/public/memes/CREDITS.md) record the
original sources, transformations and checksums. Third-party images do not
inherit the repository's software license. Humor quality is subjective; image
loading and route coverage are tested, while audience enjoyment is not a test
result.

## Failure found during live acceptance

The first dev.11 browser attempt timed out waiting for initial rendering. A
second attempt decoded every selected meme image but exposed real failed data
requests: generic authentication 403s, gateway 502s and loading panels. These
attempts are failures, not successful availability evidence. The workspace
OAuth token had not expired. Later successful single requests did not erase
the concurrent failures.

Read-only PostgreSQL activity and relation statistics showed telemetry inbox
delivery and expiry scans occupying the standalone App's two-connection pool.
The inbox contained approximately 680,000 retained rows. Parallel workers were
visible on the delivery scan, with storage I/O waits rather than blocking
sessions. Authentication, control state and collectors shared those same two
connections. This is an application query/capacity problem; these observations
do not establish a Lakebase service outage.

Dev.12 adds matching telemetry inbox indexes, bounded delivery and expiry
work, and avoids rewriting expiry values that have not tightened. The Apps
launcher defaults the shared pool to five connections and preserves explicit
operator configuration. Native-process defaults remain unchanged. Five shared
connections are not a reserved authentication pool or a concurrency guarantee.
The telemetry schema advances to version 5; an older binary may refuse that
newer schema during rollback. Keep the data and use a compatible revision.

Unavailable account storage now fails closed with retryable HTTP 503,
`databricks_app_auth_unavailable`, and `Retry-After: 5`. Organization and known
identity/link refusals retain HTTP 403. Every request resolves its durable role
again; no earlier administrator role is reused when storage fails. These
middleware responses and their warning omit raw resolver details, SQL and
credentials; this is not a guarantee about every existing application log.

The first dev.12 tour waited for every request to close, including the
intentional long-lived `/api/v1/events` stream; that harness wait failed even
though the page loaded. The next tour correctly excluded that stream and
loaded all six desktop pages plus two mobile pages, then hit HTTP 429 during
rapid navigation. The rate limit remained active at 60 requests per minute.
The corrected App keys that pre-authentication limit by the validated platform
email and workspace instead of grouping employees behind one proxy address.
Malformed or disallowed identities retain an IP bucket, and ordinary session
deployments retain their IP behavior. The final tour is paced within the
existing limit; it does not establish unlimited navigation or viewer capacity.
The first post-start catalog check still saw telemetry schema v4 and temporary
binding/erasure warnings. A later read-only catalog check confirmed v5 and all
three new indexes ready and valid; telemetry returned to `polling` with cursors
for the six configured streams. Readiness can precede this background migration.
No exact cold-migration duration or unrestricted cold-query throughput was
established.

The next paced tour completed all 12 page checks and six final API checks
(HTTP 200, approximately 89–244 ms), but still failed overall: the long-lived
event stream ended with three HTTP/2 protocol errors. The SSE handler had no
lifetime limit while the server enforced a 60-second write timeout. The final
correction ends the stream cleanly before that deadline, allowing EventSource's
existing reconnect behavior. Server timeouts remain bounded. That failed tour
is retained separately from the final stream-aware acceptance.

## Validation scope

- Frontend: 755 tests in 102 files, no skips; ESLint passes.
- Browser suite: 46 tests, no skips/retries/unexpected failures. The 22-route
  desktop/mobile tour checks same-origin JPEG decoding and layout overflow.
- Auth/API before the operational-error correction: 1,627 passing test/subtest
  events and one opt-in live skip, under the race detector with disposable
  PostgreSQL. An initial run without its PostgreSQL fixture failed three
  emergency-stop integration tests; the correctly configured rerun passed.
- Additional focused tests exercise operational storage failures, typed
  identity refusals, safe error responses, fresh role resolution, and the Apps
  default/explicit pool configuration.
- All 25 Python packaging tests pass.
- Focused command-package race tests cover shared-IP employee isolation,
  normalized identity/workspace buckets, unchanged 61st-request rejection,
  invalid-identity fallback, native/session behavior and limiting before an
  unavailable account lookup. Existing limiter/proxy boundary checks pass.
- Focused API race tests include real HTTP/2 clean-EOF/reconnect, heartbeat
  and subscription-cleanup checks. A short server write deadline plus simulated
  account-lookup delay verifies that the bounded stream deadline preserves its
  close margin; a separate timer test does not depend on caller cancellation.
- All 69 telemetry package test/subtest events pass, with race detection,
  integration/e2e tags, zero skips/failures and 79.2% statement coverage. Vet
  passes. Tests use disposable local PostgreSQL, not the monitored workload.
- A local 20,000-ACK backlog plan used an index-only candidate scan with zero
  heap fetches and one payload primary-key fetch for a late historical event;
  the warm run took 4.415 ms. It still scans ACK identities: this is not an
  O(limit) query or a cold-storage Lakebase throughput guarantee.
- Store tests cover v4-to-v5 migration/idempotence, backend/lock/acquisition
  deadlines, settings reset, canceled-transaction connection release, expiry
  refusal before erasure, 500-row committed batches, replay/ACK retention and
  no-op deadline updates. An isolated regression check restoring the old
  unconditional update failed the tuple-rewrite test as expected.
- The CLI's `apps validate` command refuses this Go-binary/Python-launcher
  package because it expects a Node `package.json`. This is an unsupported
  project type, not a strict-validation pass. Native compilation, packaging
  tests and ELF/chunk/checksum checks validate the actual deployment format.

## Corrected live deployment

The final immutable App deployment succeeded. Independently exporting its
seven runtime files produced byte-identical hashes to the reviewed package;
the launcher verifies the reconstructed binary before executing it.
Readiness reports configuration, control database and schema healthy.
Anonymous access redirects to platform sign-in. The owner resolves as the same
durable administrator through Databricks auth, without a local session cookie.
Resource bindings, user scopes, service principal and complete App ACL match
the pre-correction state, including organization `CAN_USE` and owner/admin
management grants.

Observation mode, disabled automatic SRE starts, metadata-only telemetry and
Databricks AI OAuth configuration with no API key are preserved. This follow-up
did not invoke a model again; the earlier dev.10 Gateway request proof retains
its original scope and date.

The final paced live tour passed all 12 page checks: Ask, Cases, Fleet,
Findings, Facts and the advanced dashboard at 1440- and 390-pixel
widths. All six distinct meme images decoded from the App origin, page data
requests settled, and no overflow, page errors or HTTP failures were recorded.
Ask had a selected database and rendered its input; Fleet showed a connected,
nonempty database list. All six final protected API checks returned HTTP 200
in 83–214 ms. Authentication remained platform-only, without a local session.
Six event-stream responses were observed, with five clean completions and zero
HTTP/2 protocol errors.
The tour issued zero mutation requests. This verifies those routes and one
authenticated identity in the final deployment, not every role or concurrent
employee access.

No new scenario workload, fixture changes, database grants, approved database
actions, automatic SRE starts or notification sends belong to this follow-up.
App startup applies its normal metadata schema/index migrations. Existing
natural collection remains in Observation mode with metadata-only telemetry.
This is not an unbounded load test or a new proof of every Lakebase feature.
