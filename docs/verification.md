# Verifying the verifier: the placebo back-test

pg_sage keeps or reverts a change on the verdict of its verifier. Verification v2
(attribution by blocks per call against untouched control statements, a mechanism
gate, contamination detection and alpha spending across looks; see
[architecture.md](architecture.md)) only becomes a database's verifier once it has
been measured on that database. The measurement is a back-test over the history
pg_sage already stores: it reads snapshots and the hourly rollup and writes one row.

## The method

1. **Placebos.** The back-test draws placebo steps (300 by default, with a recorded
   seed) at random times in the last 90 days of history: steps that changed nothing.
   A placebo stands where a real index step would: its targets are the statements
   on one random table (the tables each statement names, read the way
   `workload.ReferencedTables` reads them), its controls the busiest statements that
   do not name that table. One placebo in four is a "global" placebo standing for a
   setting change: the busiest statements, no control group. A placebo never falls
   within 72 hours of a real executed action on its table (or of any action naming
   no table), and never in the first three weeks of the history, so the seasonal
   match has the weeks a real step on a database this old would have.
2. **Replay.** Each placebo is watched as a real step is: verification v2
   (`verify.JudgeLookV2`, the function the index watch and the post-action monitor
   call) at every look of the schedule (2 h doubling to 72 h), with the alpha spent
   look by look, until a look decides. v1 (`verify.DecideTargets` on time per call)
   is replayed on the same windows for comparison. The mechanism gate is assumed to
   pass: a placebo has no index whose use could be checked, and assuming the gate
   passes is the worst case for a false positive.
3. **False positives.** Any `improved` or `regressed` verdict at any look is a false
   positive: it would have kept or reverted a change on noise. `neutral` is the right
   answer. A placebo the verifier never decided counts in the **inconclusive share**,
   shown so that a verifier that is too strict is visible.
4. **Detection.** The same placebos again with a synthetic 30% drop in blocks (and
   time) per call on their targets from the step onward. The **detection rate** is
   the share called `improved`.
5. **Epoch breaks.** A placebo whose windows cross a statistics epoch change (a
   reset, or a Neon or Lakebase suspend and resume) gives no measurement: it is
   excluded from every denominator and the report states how many were.

The run is bounded by `verify.backtest_max_runtime_minutes` (default 10): a run that
reaches it, or whose history cannot be read, stores nothing, so a partial rate is
never published. A database with less than 28 days of history gives "not enough
history: N of 28 days" and no row. Two runs of one database never overlap (an
advisory lock; the second says "back-test already running").

## The gate

`verify.method: auto` (the default) acts on v2 for a database when its newest
`sage.verifier_backtest` row:

- is of verifier `v2`;
- has at least **200 usable placebos** (placebos minus excluded);
- has a **false-positive rate at or below 5%**;
- has a **detection rate at or above 80%**: without this floor a verifier that never
  decides (rate 0) would pass;
- ran within the last **35 days**.

Otherwise `auto` is `shadow`: v2 is computed beside v1 and v1 acts. The rate is
compared as an exact fraction of the counts (10 of 200 is exactly 5% and passes).
The Wilson 95% upper bound of the rate is shown but not gated, so a small database
is not held back by its size alone: on 200 placebos with no false positive the bound
is about 1.9%, on 200 with ten (5%) about 9%.

The sidecar runs the back-test weekly per database on the leader, skipped while the
host guard withholds heavy work (managed-cloud replica lag, storage runway, memory
pressure). A run that fails (not enough history yet, cut short at
`verify.backtest_max_runtime_minutes`, a read error) is retried a day later, not at
every hourly check. The resolver re-reads the row every 10 minutes, so a new
back-test takes effect without a restart; a later failing row returns the database
to `shadow`.

## The rates on the bench fixtures

Five deterministic fixtures with no real step in them, each built to trip a naive
verifier: a seasonal week, a traffic shift between a cheap and an expensive
statement, a noisy neighbour in the control group, deploy breaks (statistics resets)
and targets that run only weekly. The numbers are in
[generated/verifier-backtest.md](generated/verifier-backtest.md), regenerated by
`go run ./cmd/gen_verifier_backtest` (a test fails when the checked-in page is
stale). v2 stays at or below 5% on every fixture; v1, which pools time per call by
the post-period call mix, is above 5% on the traffic shift: the back-test can fail
a verifier. The weekly-only fixture shows the inconclusive share at work: targets
that rarely run are seldom decided, and the detection floor keeps v2 from acting on
such a database.

## A database's own rate

```
pg_sage_sidecar verifier-backtest --database NAME [--config FILE] [--days 90]
    [--placebos 300] [--seed N] [--json]
```

`NAME` is a database the configuration registers (`databases[].name`, or the
standalone database). The command prints v2's and v1's counts, the rate with its
Wilson bound, the inconclusive share, the detection rate and the gate's answer, and
stores the row the gate reads (exit 0 whatever the gate says, 1 when the run failed,
2 on a usage error). It reads the history through the monitored database's
connection, so with `history.store: meta` it refuses (exit 2): such a database is
back-tested by the sidecar's weekly run, which reads the meta database. The latest rows:

```sql
SELECT ran_at, placebos, excluded, false_positives, fp_rate, fp_wilson_upper,
       inconclusive_share, injected, detected
FROM sage.verifier_backtest ORDER BY ran_at DESC LIMIT 5;
```

Rows are kept 365 days.
