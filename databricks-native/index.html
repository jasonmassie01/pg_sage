    Databricks-native implementation¶

    pg_sage 2.5.0 runs as a local native process against Lakebase or as a Go service with an embedded React dashboard in Databricks Apps. Lakebase connections and Unity Gateway AI requests use Databricks OAuth. In Apps, operators sign in through Databricks only; there is no second pg_sage login or Gateway API key.

    This is a development integration, not a claim of complete Lakebase support. The October 29–30, 2026 acceptance results establish specific paths and identities. Public platform documentation was cross-checked November 1, 2026. The tables below distinguish native-process results from App-principal results and identify functionality that remains restricted or unproven.

    The November 2 dev.11–12 follow-up adds the optional organization email-domain audience gate and recognizable, locally bundled meme images. Its new validation covers auth, packaging, telemetry storage and UI; the broader database/telemetry compatibility evidence below retains its original revision and date.

    Dev.12 corrects an availability failure found during that live UI check: telemetry inbox delivery and expiry scans competed with authentication in the standalone App's two-connection pool. It adds query bounds/indexes and an Apps default of five shared connections, preserving explicit configuration. Account storage outages return retryable 503; organization/identity refusals remain 403. This does not establish unlimited viewer concurrency or a production load test.

    Architecture and identity¶

    flowchart LR
    User[Signed-in Databricks user] --> Edge[Databricks Apps ingress: TLS and login]
    Edge --> App[Go HTTP API and embedded React dashboard]
    App --> Roles[pg_sage roles and action approvals]
    App --> SDK[Databricks SDK: App OAuth M2M]
    SDK --> PG[Direct Lakebase endpoint: PostgreSQL TLS and short-lived credential]
    SDK --> AI[Workspace Unity Gateway: model permissions]
    SDK --> SQL[Optional SQL warehouse: scoped system.lakebase reads]
    PG --> State[sage schema: findings, cases, configuration and audit]
    SQL --> History[Bounded retained history and SRE citations]

    The runtime remains Go plus embedded React. Python launch/package helpers adapt that binary to Apps; they do not replace the application or move monitoring into a notebook or Spark job. The App listens on DATABRICKS_APP_PORT, accepts HTTP/1.1 and H2C behind platform ingress, and leaves external TLS/login to Apps.

    Three authorization boundaries remain independent:

    1. Viewer identity: Apps supplies the signed-in user's forwarded email. pg_sage requires platform runtime context, maps that identity to a local role and fails closed without identity. SAGE_DATABRICKS_ADMIN_EMAIL selects the reviewed administrator. Newly created platform users are viewers; visiting first does not grant administration. Existing local accounts require reviewed identity migration. Access is trusted only behind the Apps ingress; this is not a general header-authentication mode for arbitrary proxies. Optional SAGE_DATABRICKS_ALLOWED_EMAIL_DOMAINS restricts the audience before account lookup on every protected request, including existing administrators. It matches exact email domains without accepting subdomains or suffixes implicitly. The configured administrator must match; this domain check does not prove directory employment or grant a pg_sage role. Without this setting, platform App permissions continue to control the audience.
    2. Background identity: database, Gateway and warehouse requests use the App service principal. These requests do not impersonate the signed-in user or inherit their data/model privileges. App mode pins SDK authentication to OAuth M2M and rejects PAT/profile/basic fallbacks and configured AI API keys.
    3. Database/action authority: the PostgreSQL role, object ownership, pg_sage role, trust/execution policy, approval and action-specific gates all apply. A successful login or resource attachment does not establish every database permission or authorize a SQL change.

    Locally, select a Databricks CLI profile explicitly. Native database credentials are minted for physical connections and cached until two minutes before expiry. Renewal is checked when a new physical connection opens; an established session can outlive its login token's expiry. OAuth pools verify the configured endpoint's hostname and use TLS. Use the direct endpoint: Lakebase's built-in pooled endpoint does not support this OAuth path. The singular endpoint variable affects metadata and monitored pools; use the documented hostname map when pools target different endpoints.

    In Apps, configured AI clients must remain on the exact configured HTTPS workspace origin. This applies to general/advisor, optimizer and SRE clients, including persisted overrides and model discovery. Unity Gateway still needs an allowed model route and the App principal's invocation permission. A model call proves that model/path, not universal tool or JSON support across models.

    State, resources and configuration¶

    Lakebase stores persistent pg_sage metadata in sage: accounts and role bindings, findings, cases, proposals, configuration, audit and retained history. Observation mode still bootstraps and writes this metadata; it is not a zero-write database connection. Start with a dedicated development branch and database. Reusing an existing endpoint is supported, but does not isolate cluster-wide effects of arbitrary integration fixtures.

    App local storage is ephemeral. The package can recreate the executable and listen-address configuration. Keep the encryption key in an existing secret resource, stable across restarts/deployments; preserve and migrate existing metadata rather than dropping a user-owned sage schema to repair ownership. Packages must not contain database passwords, workspace tokens or raw test data.

    Input or resource Purpose and boundary
    postgres App resource Existing Lakebase database binding; current template uses CAN_CONNECT_AND_CREATE. Verify the resulting role and actual object grants separately
    PGHOST, PGDATABASE, optional PGUSER Direct endpoint and actual database role; App launcher defaults the role to injected DATABRICKS_CLIENT_ID
    SAGE_LAKEBASE_ENDPOINT Full projects/<project>/branches/<branch>/endpoints/<endpoint> path; native multi-endpoint deployments instead use SAGE_LAKEBASE_ENDPOINTS
    sage-encryption-key secret resource Supplies stable SAGE_ENCRYPTION_KEY; do not generate a new key on every boot
    SAGE_AUTH_MODE=databricks_app and SAGE_DATABRICKS_ADMIN_EMAIL Platform-only authentication and explicit administrator selection
    Optional SAGE_DATABRICKS_ALLOWED_EMAIL_DOMAINS Comma-separated exact DNS-domain audience policy; invalid policies/admin lockout stop startup, and denied identities receive 403 before account lookup
    gateway-model resource, Gateway URL and model name Model invocation authority; llm.auth=databricks, no API key
    Optional lakebase-history-warehouse resource Warehouse CAN_USE plus appropriate UC/system-table permissions; does not grant access by itself
    lakebase_observability settings and bindings Explicit endpoint/database identity, bounds, retention and payload consent for the optional history reader
    Observation trust, executor/SRE policy and token budgets Control proposals, mutations, background investigations and AI spend independently

    Use settings.example.json, configure.py, app.yaml and databricks.yml as portable inputs. The operator guide explains which values to obtain from the deployed workspace and how to retain the full resource set when updating an App. CLI/bundle schemas vary: inspect installed help and validation warnings, including the tested model-resource schema limit.

    Install and operate¶

    For a local build, use Go 1.25+, Node.js 20+ and a C compiler. Install frontend dependencies, then build with the repository helper:

    npm --prefix sidecar/web ci
bash scripts/build-local.sh
./dist/pg_sage --version

    The helper retains libpg_query SQL AST validation. Select a profile and a passwordless, URL-encoded database role; apply the Lakebase connection configuration and Gateway configuration before starting the binary. Standalone UI login remains separate from workspace credentials used for outbound calls. Platform-only UI sign-in applies to Apps mode.

    For Apps, follow the full build/package sequence to produce a Linux artifact matching the runtime architecture with libpg_query (the recorded dev.10 artifact is AMD64). The deployment sequence covers:

    1. Inventory the existing endpoint/database, App principal, grants, secret, Gateway model and optional history warehouse.
    2. Package and configure a fresh runtime-only stage using private local settings.
    3. Preserve every resource and identity setting when creating/updating the App.
    4. Validate the package and upload only the manifest-selected runtime files using the documented raw workspace upload procedure; do not sync the repository.
    5. Deploy a SNAPSHOT and compare the deployed files/artifact hashes with the stage, then check authenticated runtime readiness and, for selected-model acceptance, an actual AI call.
    6. Retain the previous package, settings and compatible metadata/schema baseline for an operator-directed rollback. Redeploying an older binary alone does not reverse database migrations or restore a lost encryption key.

    The logs/troubleshooting table separates startup/authentication errors, ownership failures, empty telemetry, Gateway permission issues and stale browser/database state. Profile, workspace, endpoint mapping and cached provider changes require a process restart.

    The nine controlled families were duplicate index, missing foreign-key index, stale statistics, bloat, heavy sequential scans, invalid index, sequence exhaustion, slow query at the default threshold and temporary spill.     Telemetry, auto-explain, SRE and SLOs¶

    Current public Lakebase telemetry documentation describes Beta preview automatic capture into system.lakebase while compute runs; legacy provider observability configuration objects no longer receive data and cannot be created. pg_sage's explicit reader bindings select the intended physical endpoint/database. They are not instructions to create those retired objects. Warehouse/UC access, project opt-in where applicable, payload consent and unmasking are separate prerequisites. Follow the current platform and reader details.

    Provider plan_history is distinct from installing or controlling ordinary session auto_explain. With explicit consent, structured payloads can enter the provider-plan cache; metadata-only operation retains bounded structured observations and provenance without raw SQL, plans, log bodies or actors. The native controlled capture proves positive delivery. Earlier zero-row reads remain dated failures/inconclusive observations, not proof of platform absence or later complete delivery.

    Without Advanced Telemetry, catalog/query-statistics collection and supported live read-only SRE probes still work within privileges and database-only policy. Telemetry adds retained plan/log/session/DDL/database observations, cited by the read_history tool. Neither a positive history row nor a readable empty probe proves the current incident's cause. History is delayed and cannot satisfy live CPU/I/O admission or establish every lock, connection, WAL or pressure scenario. See SRE with and without telemetry.

    Application SLO evaluation requires explicitly bound application counters. Apps offers administrator-only authenticated sample ingestion with durable database/objective scope, actor-bound series and replay/conflict checks. Stale samples become unknown. The synthetic lifecycle is tested; a complete production customer SLO is not established by that test or by provider logs.

    The statistics-maintenance bridge requires a retained investigation, fresh evidence, exact physical object identity, human approval and the existing typed executor gates. Native owned-table proposal, execution, structural verification and rollback were tested. Rollback cannot restore old ANALYZE statistics and does not prove performance improvement or incident recovery. Separate coordination-database retention holds are unsupported. Read the maintenance contract before changing permissions or execution policy.

    Understanding Cases, Actions and Ask Sage¶

    Cases explain what was observed, the possible consequence, what is missing and a supported next step. Technical evidence remains expandable. Unknown urgency, size, impact and recovery are shown as unknown; absence of a measurement is not a successful safety check. Suppression hides a condition rather than fixing it.

    Actions separates Proposed changes, Needs your review, In progress and History. An accepted approval, completed SQL and a verified outcome are different facts. Execution mode is separate from operational risk. Equivalent action aliases consolidate into one review item, while saved proposals retain their own risk/recovery claims. Old recovery SQL is withheld when it does not match the current procedure; unnamed indexes do not receive guessed inverses. Lakebase-inapplicable system-setting procedures are withheld.

    Cases → Actions → Ask preserves database/case context. Explain prepares a draft for the user to send; it does not automatically start an AI request. A single running database is selected automatically, and loading/error/empty states are distinct. Fleet includes actual running/configured databases. The observatory theme is responsive, with compact DBA meme images on each page and monitoring scope/mode context before the content.

    Dev.11 replaces the original illustrated jokes with six recognizable classic image templates and route-specific HTML captions. Images are bundled in the binary, lazy-loaded and served from the App origin; the browser does not fetch them from a meme CDN. Template provenance and rights notes record sources, attribution, transformations and hashes. These third-party images do not acquire the repository's software license.

    Dev.13 moves the breakroom above page content and expands it to 50 distinct captioned memes on those six templates. A shuffled deck survives navigation without repeating until all 50 are used; reloading starts a fresh deck. It advances on page changes or every 60 seconds, with Another meme and pause/resume controls. Background tabs and focused meme controls do not consume cards; reduced-motion users start paused. No database or AI requests drive rotation. Standalone Settings also accepts the running database's absent/zero managed ID after the server confirms standalone mode, and labels configuration as instance-wide. Managed fleet databases retain their database-specific scope.

    Dev.14 adds a short description of the current tab beside the meme on desktop, wrapping below it at smaller widths. Guidance stays fixed while memes shuffle, and reflects filtered Cases links, access restrictions and the App's disabled agent/MCP workflows. It describes the page; it does not infer database health or grant access to a feature.

    These changes address heuristic usability findings. Actual novice usability testing and explicit synthetic-fixture labels in Cases remain outstanding; the UI does not infer that arbitrary schemas are synthetic from their names.

    Reproduce safely and track remaining work¶

    Run ordinary local integration suites against disposable PostgreSQL. Their role changes, shared-statistics resets and instance-setting attempts are not a portable Lakebase full-suite recipe. The dedicated Lakebase checks document explicit opt-ins and native targets. Packaging can be checked without a workspace:

    python3 -m unittest discover -s deploy/databricks-apps -p 'test_*.py' -v

    The optional controlled fixture helper requires an explicit profile, endpoint, direct host, database and user, through CLI flags or SAGE_NERDLAB_*. Run --help first. It manages only nerdlab_20261030, keeps an exact-identity/object ledger under private .local-test-results/, refuses reuse or changed inventory and enforces a cumulative 110-scan budget. Keep the same manifest between commands; do not delete it to repeat an exhausted budget. seed, exercise, slow-query and cleanup intentionally change the selected development database. preflight inspects identity, while status verifies the ledger and reads findings. No fixture command runs automatically during deployment.

    Remaining compatibility work includes App-principal workload-table maintenance, App raw plan-cache ingestion, latest-artifact credential endurance, multiday and failover behavior, most sustained incident/pressure families, complete provider delivery/latency guarantees and real novice comprehension. Provider restrictions on hints/HypoPG and unsupported Apps agent protocols remain explicit. Measure each item on an isolated authorized target; retain an incompatibility when no supported workaround satisfies the original contract.
